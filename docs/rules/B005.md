# B005 thread-builtin

## What it does

Reports `thread foo()` (or `ent thread foo()`, `childthread foo()`) where `foo` is a builtin and no script function the threaded call can reach has that name: one of the caller's namespace (`namespace-first`), or of the file and its `#include`d files (`file-first`, `builtin-strict`). In `file-first` games it also reports a function reference `::foo` to a builtin, and in `builtin-strict` games every `::foo` naming a builtin, even when a script function of that name exists.

Only games whose profile sets `bare_call_resolution = "namespace-first"` (T7, and T8 to T11 after acts' Black Ops 4 linker and compiler), `"file-first"` (World at War, Call of Duty 4 and Black Ops, measured in their VMs) or `"builtin-strict"` (Black Ops II, measured in its VM) are checked. The rule needs the game's complete builtin catalogue, and skips decompiled files (see [B004](B004.md)); the T4 and IW3 catalogues are not complete yet, so it is silent there for now.

## Why

A threaded call links to script functions only. In Black Ops III the game's linker reports `Unresolved external` for `thread spawnstruct()` and refuses to load the script (measured in the game's VM: `gruff-data/semantics/t7.toml`, `thread_call_builtin_only`). acts' reimplementation of the Black Ops 4 linker does the same, and its compiler rejects "thread modifier on a builtin call"; in the retail bytecode of Black Ops 4 and Cold War, no threaded import names the empty namespace their builtin calls use. A plain call or `&foo` does fall back to the builtin.

In World at War and Call of Duty 4 the game's own compiler, which runs when the script loads, refuses both `thread spawnstruct()` and `f = ::spawnstruct;` with "unknown function" when no script function of that name exists (`gruff-data/semantics/t4.toml` and `iw3.toml`: `thread_call_builtin_only`, `func_ref_builtin_only`). A plain call does reach the builtin, before the functions of the `#include`d files.

In Black Ops II the game's linker (which links scripts compiled elsewhere) looks a bare call up in the builtins before any script function, even one of the same file; a threaded call goes to the script functions only and fails to load with `Unresolved external` (`gruff-data/semantics/t6.toml`: `thread_call_builtin_only`). A function reference `::foo` takes the same builtin-first lookup, but the linker stores the builtin's native handler where script code belongs: calling the reference runs that machine code as bytecode (a garbage script error, then "unhandled script vm exception"; `func_ref_builtin_only` and `func_ref_shadows_builtin`, unsupported for that reason). Such a reference is never what the author meant; a path-qualified one (`maps\mp\_utility::foo`) reaches a script function named like a builtin.

## Example

```gsc
function f()
{
    self thread playsound( "beep" );   // B005
    self playsound( "beep" );          // fine
    self thread play_beep();           // fine: a script function that calls the builtin
}

function play_beep()
{
    self playsound( "beep" );
}
```

## How to suppress

On the line (or on its own line just above it):

```gsc
self thread playsound( "beep" );  // gsc: ignore[B005]
```

For a whole file, anywhere in it: `// gsc: ignore-file[B005]`. In `gruff.toml`:
`ignore = ["B005"]`, or `[check.per-file-ignores]` with `"pattern" = ["B005"]`.
