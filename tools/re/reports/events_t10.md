## How the notify core was found

No event hash in the code: events are 32-bit script-string ids. scr_const: three inits call the getter 0x81c1480 (&out, char*, 0x20, 1) 2501 + 382 + 59 times with the strings in clear (an encrypted-string flag in the first byte is never set on them), each id then stored in a global. Of the 87 code references to the slots of `death`, `damage`, `trigger`, `movedone`, `weapon_fired`, `goal`, `reload`, 29 load the id right before Scr_Notify(ent, event, count) 0x59a3400 (395 callers) -> Scr_NotifyNum 0x81de400 -> VM_NotifyVm 0x81e2cd0 (vm, object id, event, count), BO7's core (pops the pushed values off vm + 0xc4a8, tags the frame 0x10, calls VM_Notify 0x81e4400); Scr_NotifyLevel 0x81de3e0 reaches it too. A second path does not go through it: the only other function that reads the in-param count (ctx + 0xc480) and tags the frame 0x10 is 0x81d7810, whose one caller VM_NotifyCtx 0x81d7660 (ctx = vm + 0x30, event, object id, count, callback) is called by 0x81d7630 (level), 0x81d75c0 (entity) and 0x81d77d0 (with a callback); both are cores of this extraction. Value tags: T10_TAGS in treyarch/events.py. The VM is 0xb27d730 (the server VM of the builtin sets); no client VM is located in this dump. VM attribution: VM_NotifyVm reads its VM from the context inside Scr_NotifyNum, which the wrapper probes see as 0, so the sites of that path carry no `vm`. The campaign dump (merged) the same way: getter 0x4c53cd0 (inits 0x5f899b0, 0x5f9d530, 0x5fa0920: 2249 + 375 + 59 calls, strings in clear), Scr_Notify 0x6be2910 -> Scr_NotifyNum 0x4c6f2a0 -> VM_NotifyVm 0x4c73c40 (VM 0xabd3a00, stack top at VM + 0x8388), VM_NotifyCtx 0x4c67600 (the caller of 0x4c67780); its value tags differ from multiplayer's (T10SP_TAGS).
